# C++ object model: where the port should end up (decided 2026-11-10)

Status: **accepted by naari3 on 2026-11-10 14:56Z (the recommendation below).** Background is
`census.md` section 13 and `upstream_requests.md` item 14.

## The problem in one paragraph

The original game is ordinary C++ compiled by MWCC with RTTI on. The
decompiled source does not say so yet: most polymorphic classes exist as
per-unit copies under invented names, their vtables are arrays written out
as data in MWCC's layout, many constructors are C functions that store the
table address by hand, and pointer-to-member tables are `{0, -1, fn}`
triples. MWCC produces the original bytes from that. Any other compiler sees
two views of the same object that only agree under MWCC's ABI.

Measured on mkgp2-decomp `c5dc13e`:

| | count |
| --- | --- |
| vtables in `symbols.txt` | 300 |
| of those, emitted by the compiler from a class definition | 45 |
| of those, written by hand as `void *X_vtable[N] = {...}` | 255 (250 in `src/game/autodata`) |
| class names the rename table maps onto those 300 tables (`__vt__Name`) | 1,483 |
| class/struct definitions that declare a `virtual` | 937 (739 distinct names, 11 with two bases) |
| lines that store a vtable address by hand | 179 in 106 files |
| lines that call through a table by hand | 186 in 179 files |
| pointer-to-member types / call sites | 24 / about 10 |

## What other ports do

Checked in the sources, not from memory:

- **Dusklight** (Twilight Princess, `TwilitRealm/dusk` at `77705f8`, built on
  Aurora and on the zeldaret/tp decompilation): no ABI layer at all. The
  decompilation is real C++ (about 3,000 `virtual` declarations, about 600
  pointer-to-member uses, no vtable written as data), so the host compiler
  builds every table itself. Port changes are made in the source under
  `#if TARGET_PC` with the original kept (`docs/code-conventions.md`);
  big-endian file data is typed `BE(T)` (`include/helpers/endian.h`). It
  ships for x86-64 and arm64.
- **Metroid Prime port** (`Odrannnn/MetroidPrimePort` at `49e2711`, on the
  PrimeDecomp decompilation): the same. `__vt__` appears only in
  `symbols.txt`; 64-bit Android and iOS builds exist.
- C ports (Melee, Animal Crossing, Mario Party 4) never meet the question.

Nobody found rewrites compiler output. The reason is not that they chose a
different bridge: they do not need one, because their source already is the
C++ the game was written in. Our ABI problem is the same debt as the
"about 700 class copies" left over from struct clean-up, seen from the PC
side.

## Options

**A. Keep rewriting the host compiler's output (today's
`port/tools/mwcc_cxx_abi.py`).** No source change, works now for the vtable
address point and the destructor slot, and compiler-emitted tables come out
in the same convention as the hand-written ones, so both kinds of class can
coexist. Costs: game C++ must go through clang with the Itanium ABI and a
textual IR pass (LTO type tests and debug info required), so MSVC is out; the
position of the vtable pointer, classes with two bases and virtual
pointers-to-member are not handled and are the hard parts. Checked here with
clang 18: for `i686-pc-windows-msvc` clang emits the Microsoft model, which
the pass does not understand; `-fc++-abi=itanium` on that target does not
terminate; the MinGW-style target (`i686-pc-windows-gnu`) does give Itanium
IR, but member functions there are `thiscall` while the functions in the
hand-written tables are plain C functions, a mismatch that 32-bit Linux
(where the pass was proven) does not have. As a permanent answer it also
leaves the hand-written layouts in place, which is what blocks 64-bit.

**B. Make the source say what the game is: one real class definition per
class, vtables and pointer-to-member constants generated by the compiler.**
What every other C++ port has. Done in mkgp2-decomp, class by class, each
step byte-identical under MWCC (45 tables already are emitted this way, and
`-inline deferred -RTTI on` placement is understood). It removes the
problem instead of bridging it, is the only option that also clears the way
for MSVC and 64-bit, and is work the decompilation wants anyway. Costs: 255
tables and about 1,400 alias names to fold; some classes will not come out
byte-identical on the first try and stay as they are for a while; it cannot
be finished before the port needs to run.

B is really three steps of very different cost, and the pilot has to price
each:

- B1, one definition per class: fold the per-unit alias classes into one
  header definition. Mechanical and tool-driven like the struct merges
  (MWCC's code depends only on the layout and the slot numbers), and needed
  by every option, 64-bit included.
- B2, real constructors and member functions in place of C functions that
  store the table by hand. Usually the same code, checked per function.
- B3, MWCC itself emits the table. This is matching-grade work: the owning
  unit needs `-RTTI on`, often `-inline deferred` (which reverses function
  order), and the right data order (matching_rules section 6). If B3 turns
  out slow, the bridge can still be retired earlier by generating the host's
  tables from the hand-written arrays once B1 and B2 are done for a class.

**C. Make the object model explicit in the source for other compilers**
(plain structs with a vtable-pointer member, `VCALL` macros at every virtual
call, under `#ifndef __MWERKS__`). Compiler-independent and solves the
vtable-pointer position, but it touches every polymorphic class and call
site, moves the source further from real C++, and all of it is thrown away
when B reaches the class.

## Recommendation

**B is the destination; A stays as a bridge with a fixed scope and an exit;
C only for single classes that block a milestone.**

1. Decide now that the end state is B, so nothing new is designed around
   MWCC-layout tables. A is safe to keep meanwhile because it is a build
   step: game code written on top of it does not know it exists, and it
   treats compiler-emitted tables the same way, so classes can move to B one
   at a time without a flag day.
2. Freeze A's scope at what it does today (address point, destructor slot)
   plus the calling convention if 32-bit Windows needs it. Do not teach it
   vtable-pointer positions or multiple inheritance; the roughly 17 classes
   with members in front of the pointer go to the front of the B queue, or
   get C locally if one blocks the first frame.
3. Before more is built on A, check it on the Windows machine with one C++
   unit (MinGW-style clang target, see above). If that is not workable, the
   interim Windows target is 64-bit or the bring-up stays on Linux until B
   has covered the classes on the boot path.
4. Start B with a pilot of about ten classes on the first-frame path (the
   scene family) to measure how often a conversion stays byte-identical and
   how long one takes; plan the rest from that number.
5. Track it: add "hand-written vtables" (255 now) and "class alias names"
   (1,483) to `tools/port_readiness.py`. When the first reaches zero and the
   pointer-to-member tables are real `&Class::Method` constants, delete the
   IR pass and the 12-byte `PMF_*` structs; from then on the port builds
   with any compiler.

Pointer-to-member macros (`PMF_TYPE` / `PMF_CALL` / `PMF_OF`, item 14) fit
this plan as they are: small, source-level, and they turn into the plain
C++ syntax when the tables become real constants.

## What changes if accepted

- Port thread: keeps going on the IR pass, does not extend it (point 2),
  runs the Windows check (point 3), and hands over the list of classes on
  the first-frame path.
- mkgp2-decomp: a new line of port-readiness work, "turn hand-written
  vtables into real classes", starting with the pilot; one dated line in
  `docs/matching_rules.md` section 0 and a board post, since it touches
  shared headers. The matching build stays byte-identical throughout.
